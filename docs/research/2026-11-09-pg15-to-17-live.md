# Supabase Postgres 15 to 17: pgmig move vs in-place upgrade, live runs (2026-11-09)

Question: a large Supabase project on Postgres 15 has to reach 17. How long is
the write-stop window with pgmig (logical replication into a new 17 project,
then cutover) against the platform's in-place upgrade at the same data size,
and what does each lose or need?

Shape: throwaway projects on a Team-plan org, ap-southeast-1, Small compute,
created with `postgres_engine: "15"` (PostgreSQL 15.19) for the source or the
in-place subject and the platform default (PostgreSQL 17.11) for the pgmig
target. The seed is the annoying schema (`test/annoying-schema.ts`, a STORED
tsvector on `documents`). Large runs grow each disk to 20 GB first
(`DISK_GB`, `test/disk.ts`). Harnesses: `test/live.harness.ts` with
`SRC_ENGINE=15` and `test/inplace-upgrade.harness.ts`. The run logs stayed on
the machine that ran them and are not archived in this repo; every number below
is copied from those logs.

## Results

### pgmig, 50,000 documents (0.06 GB), commit 5604438

| step | value |
|---|---|
| versions | source PostgreSQL 15.19, target PostgreSQL 17.11 |
| initial copy (replicate + watch) | 5.4 s |
| reconcile (256 buckets, 4 tables) | 0.8 s, identical |
| cutover (no writer running, so this is the write-stop window before the app repoint) | 1.6 s |
| post-cutover insert | id 50001, as expected: the sequence resync prevented a collision |

Doctor warned on the Small 17 target: `max_worker_processes=6` (asks for 16 or
more), `max_logical_replication_workers=4` for 4 tables (asks for 5 or more),
and `pg_stat_statements` 1.10 on the source against 1.11 on the target.

### pgmig, 4,000,000 documents (source 3.65 GB)

- Default disk (commit 5604438): the seed failed after about 6 minutes with
  `cannot execute INSERT in a read-only transaction` (SQLSTATE 25006), the
  platform making the database read-only as the volume filled. Fixed with
  `DISK_GB` (a31ec13).
- 20 GB disks, two runs (a31ec13, then 6d11e53 with failure diagnostics): the
  `documents` table sync never finished. With 6d11e53 the target logged
  `could not receive data from WAL stream: ERROR: canceling statement due to
  statement timeout` and the source `canceling statement due to statement
  timeout` every 120 s (08:43:58 to 09:14:02 UTC), `sync_error_count` 16, the
  other three tables `r`; watch stopped at its 30 min limit. The source's
  `pg_db_role_setting` holds no statement_timeout for `postgres` (only `anon`
  3s, `authenticated` and `authenticator` 8s); the Supabase timeouts page says
  "`postgres`: none (capped by default global timeout to be 2min)"
  (https://supabase.com/docs/guides/database/postgres/timeouts). The
  subscription CONNECTION is dialled by the target's tablesync worker, so the
  pools' pinned `statement_timeout=0` never reached it, and any table whose
  initial COPY outlasts two minutes restarts forever.
- Fix (ae33443): `withNoStatementTimeout()` adds `options=-c
  statement_timeout=0` to the subscription CONNECTION unless one is set.
- Re-run with the fix (ae33443), 20 GB disks, 09:16 to 09:40 UTC:

| step | value |
|---|---|
| seed | 643.1 s; source database 3.65 GB |
| initial copy (replicate + watch) | 196.9 s; 4 of 4 tables `r`, WAL retained 10MB at the end |
| reconcile (256 buckets) | 62.6 s, identical: `users` 50000, `documents` 4000000, `events` 4000000, `audit` 400000 |
| cutover (no writer running; write-stop window before the app repoint) | 1.6 s; lag drained to 0.0 KB |
| post-cutover insert | id 4000001, as expected |

### In-place upgrade, 15.19 to 17.11 (target image `supabase-postgres-17.11.0.018`)

Eligibility answered `eligible: true`, `duration_estimate_hours: 1` at both
sizes. A 1 s probe writer inserted numbered rows through the session pooler
throughout; a 2 s sampler opened a fresh pooler connection each time.

| | 0.06 GB (commit 5604438) | 3.65 GB (commit 6d11e53) |
|---|---|---|
| POST to `5_initiated_data_upgrade` | +164 s | +153.5 s |
| data upgrade (`5_` to `6_completed_data_upgrade`) | 122.5 s | 142.8 s |
| POST to `9_completed_upgrade` | +317 s | +337.1 s |
| POST to project ACTIVE_HEALTHY | 337.4 s | 633.1 s |
| first answer from 17.11 (sampler) | +318.8 s | +344.6 s |
| longest run of failed samples | +246.3 s to +256.3 s | +235.3 s to +270.4 s |
| probe writes acknowledged / absent on 17 | 458 / 53 | 691 / 52 |
| 15.19 postmaster starts the sampler saw | the original plus 2 restarts | the original plus 3 restarts |
| server that acknowledged the absent ones | the last 15.19 restart | the last 15.19 restart |

An earlier 3.65 GB run (a31ec13) reached ACTIVE_HEALTHY at 695.5 s with a
142.9 s data-upgrade stage; its survival check failed on a client-side
`getaddrinfo ENOTFOUND`, which is why the harness now retries that read and
can dump the acknowledged ids to `ACKED_FILE` first.

Readings (inference, one run per size):

- The data-upgrade stage barely moved with size (122.5 s at 0.06 GB, 142.8 s
  at 3.65 GB), and the database answered on 17.11 at +318.8 s and +344.6 s.
- What grew is the time between `9_completed_upgrade` and ACTIVE_HEALTHY:
  20.4 s at 0.06 GB, 296 s at 3.65 GB, while 17.11 was already answering. That
  fits the post-upgrade `pg_basebackup` the upgrade guide describes
  (https://supabase.com/docs/guides/platform/upgrading). The extra 276 s for
  the extra 3.59 GB (3.65 minus 0.06) is about 80 s per GB, which is what the
  guide's "~100Mbps" gives if read as 100 megabits a second. Not separated:
  what that tail is, and whether the Data API answers during it (the sampler
  only used the session pooler).
- Every absent write was acknowledged by the last 15.19 restart before 17.11
  answered; none acknowledged by the original 15.19, an earlier restart or
  17.11 was lost. This matches supabase-lab
  `upgrade-integrity` UI03 (2026-10-23 and 10-26, Micro), now on a Team org,
  Small, a newer target image and 3.65 GB.

## Side by side at 3.65 GB (one run each)

| | pgmig (ae33443) | in-place (6d11e53) |
|---|---|---|
| writes must stop for | 1.6 s of cutover, plus the app repoint | the whole upgrade, from before the POST: the first lost write was acknowledged at +272.9 s and 17.11 first answered at +344.6 s |
| client-visible outage in the run | none measured (no writer, no repoint in the harness) | longest failed sample run 35.1 s (+235.3 s to +270.4 s) |
| acknowledged writes lost | none possible after a drained cutover (reconcile identical) | 52 of 691 |
| what changes for the app | new project URL, keys and connection strings | nothing |

## Not measured

- An app writing through the pgmig cutover, a repoint, or a source with Auth
  users or Storage objects to carry.
- Any compute larger than Small, any region but ap-southeast-1, more than one
  run per size, databases larger than 3.65 GB.
- Whether the in-place tail scales linearly past 3.65 GB, and what the Data
  API does during it.

Cost: not metered. Every project was deleted by its harness's teardown.
